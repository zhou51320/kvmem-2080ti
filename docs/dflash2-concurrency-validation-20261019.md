## Workloads and interpretation

The real target is the existing Qwen3.8-27B GSQ-RCO IQ3_S model. llama.cpp uses its separate Q4_K_M DFlash2 companion; NInfer uses the existing combined IQ3_S/vision/MTP/DFlash2 artifact. The synthetic llama.cpp tests use Qwen3.5-0.8B Q8_0 and the deterministic untrained fixture described in the [initial qualification](speculative-validation-20261019.md).

Text probes use logical context 4096, B512/R256, prefill 128, sink/recent 64, fixed five drafts and n-gram off. Target KV is q8_0 for llama.cpp and INT8 for NInfer. All-GPU real llama.cpp tests retain default ReplaySSM; the 0.8B fixture and CPU-offloaded profiles use snapshots. NInfer uses FP16 GDN and a 64 MiB graph allowance. Long prompts contain about 1054-1056 tokens, exceeding the selected window, and use different secret words per conversation. Short prompts contain about 63-65 tokens and continue for 128 generated tokens so slow cold prefill does not prevent four decode requests from overlapping.

The checks combine an explicit secret-word oracle, native accepted/drafted bounds, actual active-slot observations, historical cache-hit evidence and successful requests after a client disconnect. Exact isolated/concurrent output is an additional check, not the only correctness oracle. For the same-card stage check, both isolated outputs also match the corresponding single-stage outputs. No trained-head quality or general throughput conclusion follows from these prompts.

NInfer C4 short-prompt statistics record 847 accepted candidates out of 878 submitted, with five fallback steps. These are functional-path observations, not representative acceptance or speed measurements. C4 long-prompt admission is not advertised as four simultaneous prefill operations: upstream prefill scheduling remains serial/chunked, and completion duration influences observed active concurrency.

## llama.cpp shared-weight repair and remaining C4 constraints

The original server shared main-model weights, while each lane separately called the native companion initializer and loaded another draft weight copy. Four copies of the trained companion plus per-lane target/draft state exceeded the tested card's dedicated memory capacity, even at the small B/R above.

Windows GPU Process Memory counters for the owned C4 probe recorded 16,798,728,192 dedicated bytes and 1,616,904,192 shared bytes, approximately 1.51 GiB shared. Its first 128-token prefill chunk took 22,470 ms. This diagnostic establishes an unusable capacity spill in that setup; it is not a completed C4 correctness run or a controlled benchmark. The process was deliberately stopped after recording the evidence.

The user approved one shared, read-only native draft model/weight owner, with a separate draft context, KV cache, sampler and rollback state for each lane. This is implemented through native `common_speculative_init_result` ownership and the server's lane initializer. The target weight owner outlives the companion because the native companion may borrow target embedding/head tensors. This preserves upstream native speculative execution. NInfer already stores one embedded draft weight set in its shared model and batches per-request draft state; no corresponding NInfer ownership repair is needed.

A dedicated native lifetime test releases the first draft context and its external owner, then drafts through a surviving context, compares candidates against an independently loaded companion, and confirms final-owner release. It passes on the 5060 Ti with the small deterministic fixture. Shared-weight C2 also passes the real 27B state/concurrency checks, and the small-model CLI produces the same 24 greedy tokens with ordinary, MTP3 and synthetic DFlash2-5 execution. Exact token agreement is additional evidence alongside the state/lifetime checks.

The shared C4 log has one companion load and three reuses, one identical model pointer and four distinct context pointers. At ready, Windows counters record 14,377,816,064 dedicated bytes and 153,092,096 shared bytes on the selected GPU. Nevertheless, successive cold long-prompt requests grow per-context runtime buffers; the fourth fails at `cuMemSetAccess` with `device not ready`. A separate 32 GiB-pool diagnostic DLL reports `cuMemGetInfo` success and zero free bytes before requesting 171,966,464 bytes. This is capacity evidence, not evidence of a shared-model lifetime error. The original failure repeats without Windows counter collection.

An isolated 16 GiB virtual-reservation probe fails at the same mapping operation, and an unchanged allocator run with `GGML_CUDA_DISABLE_GRAPHS=1` also fails. Neither diagnostic changes the product allocator, default graph policy or native kernels. Shrinking virtual-address reservation is not a demonstrated solution.

After the user selected CPU offload for the next C4 check, `-ngl 56` correctly hit the existing ReplaySSM support guard, which requires GPU recurrent layers. The existing snapshots setting permits `-ngl 48` to load, but the first long request fails with `KVMem native layout copy failed` and a subsequent stale-checkpoint rollback error. A separate ordinary C1 request, with no draft context, reproduces this. The whole `layout_gpu_slots_by_orig_pos` function is identical to integration base `1b9cc6be00dcbd2959e23c8c7ee60efeeb66ba93`. Its `!multi_gpu_` fast-path test admits CPU KV tensors, then its CUDA pointer conversion fails. Packed-byte checks before the error show no sampled KV mismatch; these checks do not establish post-transfer correctness.

Finding L022 in the workspace legacy-findings log records the origin, trigger, independent control and impact. After the user's instruction to continue, the repair checks actual tensor storage before any layout copies and uses the existing backend tensor get/set host path for mixed CPU/GPU storage. The original ordinary long request now returns HTTP 200 and the known READY response. An extended existing native checkpoint-tail test accepts a GPU-layer argument and explicitly selects sparse resident blocks 0 and 2 before eviction. With the small 0.8B model split at 12 GPU layers, the same test fails with `KVMem native layout copy failed` against the isolated pre-fix DLL and passes against the fixed DLL. Both unaligned tails (65 and 95 rows) pass exact native-byte restoration, coverage-gap rejection and independent fresh-prefill recovery. The full-GPU version of this byte test and the real full-GPU C2 state/history/cancellation probe also pass after this fix.

The mixed CPU/GPU C4 probe uses 40 GPU layers and existing snapshots, leaving its other long-prompt settings unchanged. Four isolated and four concurrent requests complete, with four active slots and all secret-word checks passing. In the final run after both fixes, Windows counters after the concurrent requests record 14,717,419,520 dedicated bytes and 1,136,656,384 shared bytes. This is a CPU-offloaded workload with host staging, not a zero-shared-memory or all-GPU result. No throughput comparison is made.

Before the capture repair, both ordinary C1 and DFlash2 C4 follow-ups reproduce `backend->iface.event_record != NULL` in `ggml-backend.cpp`. The inherited capture pipe caches a CUDA event while its per-batch selected backend can later be CPU. Its complete `d2h_submit` implementation remains identical to the integration base. Finding L023 records this separate inherited defect and the user's subsequent approval to repair it.

The adapter now admits asynchronous capture only when all capture tensors are device-backed and share one GPU producer, and any cached event belongs to that device. Other captures synchronize the scheduler and drain older asynchronous captures before using the existing per-tensor host path. Draining preserves update order and avoids concurrent writes to shared host capture state. The original ordinary C1 continuation returns READY and reuses 1008 prefix tokens; its trace explicitly enters the synchronous fallback. The C4 final worker completes the full text probe, with four active slots, 13 request records, history hits of 1053/1053/1055/1054, and successful recovery after closing an output stream. Native counters record 433 accepted out of 505 drafted tokens, 101 rounds and zero speculative fallback steps; these are functional observations, not acceptance or throughput benchmarks.

The final all-GPU C2 probe also passes, retaining asynchronous GPU harvest in its trace and no mixed-capture fallback. Native checkpoint-byte checks pass in both mixed and all-GPU placements after the capture repair. The final CPU-offloaded C4 image smoke check correctly distinguishes red/blue images and reuses 42 prefix tokens on each follow-up, alongside two text callers. The existing session-restore regression accepts `--gpu-layers` and `--expect-mixed-capture` for future mixed-placement runs; this phase uses the focused ordinary continuation and full C4 probe, not a new long-context campaign.

## Probe isolation, build and test corrections

Probe translation units were copied outside the product tree. The llama.cpp probe only removed its concurrency admission predicate; the NInfer probe only widened the concurrency/device admission predicates. Original source hashes were checked before promotion. The final product promotes only C2/C4 respectively and continues rejecting multiple physical devices. NInfer recompiles the changed serving and model-admission CPU units while reusing unchanged native model/kernel libraries; no new kernel tuning is involved. Compiler concurrency is bounded to eight jobs.

Three harness issues were corrected without product execution changes: the small model naturally ended one response after 24 tokens, so requiring exactly 64 was invalid; NInfer reports cached tokens in `usage.prompt_tokens_details.cached_tokens`, rather than llama.cpp's extra usage field; and the standalone native-options test initially linked the application entry object because of an incorrect object-path match. Corrected runs and earlier unsuccessful attempts are retained locally. The C4 long-prompt overlap limitation and the real llama.cpp C4 capacity spill remain adverse/partial results, not converted into passing rows.

The machine-readable [qualification summary](benchmarks/dflash2-concurrency-20261019.json) preserves successful, failed and partial cases. Shared-weight ownership and mixed-storage layout/capture selection are implemented; CPU-offloaded real-model C4 is qualified and the common launcher limit is four. The tested all-GPU 27B C4 profile still exceeds capacity. Real cross-GPU pointers/transfers, wider parallel draft counts, parallel n-gram combinations and long-context performance remain outside this record.
