# llama.cpp v0.7.0 基础接入

> Device identifiers and private paths have been anonymized; reported measurements are unchanged.


接入工作和性能测量基于 KVMem `203e7d90`；提交前同步 master `c88e7b24`，
保留 PR #143 的 NInfer tool-open token 修复。后端固定到官方 v0.7.0：
`620d2225cc436ab0b001e3200e590e3b286ef9ab`。
后端仍由原生提交加版本化补丁重建，完整树和补丁校验值记录在 `backends/versions.json`。

## 范围

- 公共 KVMem 内存契约和其他后端接口保持不变。
- 文本预填充、验证批次改用上游 `common_batch` / `llama_batch_ext`；MTP 隐藏状态使用原生 state embedding 接口。
- KVMem 的逻辑位置随批次分割、重排和 MTP 追赶传播；未提供逻辑位置时保留原生路径。
- 保留 v0.7.0 的 GDN 四列计算和 MMA 预填充路径。KVMem Record 不写入已提交状态，Fold 只提交接受的前缀。
- 提示词和输出解析适配上游的新输入结构、PEG arena 和分段提示词结构。工具解析规则由上游模板生成。
- 监控读取原生层的设备信息通过 llama 适配器封装，支持 Windows 共享库构建。
- Qwen MTP follower 从 KVMem 执行域获取目标；不设置原生 `ctx_other`，避免被 v0.7.0 误判为共享 KV 模式。
- 适配器内存描述符中的后端版本更新为 `620d222+kvmem-native-v1`，公共契约和 attention payload 格式不变。

本批不增加概率 MTP、新的 draft ubatch 调优项或 UI 控件，不包含 v0.7.0 之后的开发版优化。

## 核心验证

首轮 8 项检查通过：GDN Record/Fold、GDN 输出融合、推理预算、聊天模板、工具调用 ID、Responses、公共内存契约和前缀检查点。
GDN 检查包括接受前缀、拒绝区 NaN、不变的已提交状态，以及独立双精度递推参考。
23 个公共头文件的 SHA256 与接入前一致。纯上游加补丁可精确重建版本清单中的源码树。

实际服务端额外通过：27B/MTP/replay 普通聊天、流式必选工具调用及空参数 `{}`；
5050/0.8B 的六轮尾部消息改写和前缀检查点复用，后四轮分别复用 1777/1809/1841/1873 行。
Windows 静态构建专用的 MTP/KV 测试已完成新版 API 编译检查，未运行其完整组合矩阵。

## 性能测量方法

手工驱动 `tests/llama-backend-perf.cpp` 默认不参与构建；需要时启用 `KVMEM_BUILD_PERF_TOOLS`。
同一份源文件也可直接链接到纯原生 v0.7.0 的库，以排除不同 HTTP 接口和聊天模板的影响。

- GPU：RTX 5060 Ti，UUID `GPU-B`。
- 同一 IQ3_S GGUF、同一份 36864 个输入 token、固定 256 个输出。
- B=36864，R=16384；原生及关闭 KVMem 时 ctx=53248，开启时逻辑 ctx=131072。
- batch=ubatch=512，目标 KV q8_0，draft KV f16，MTP=3，greedy，屏蔽 EOS，无提示词复用。
- 主对照：原生、补丁构建但关闭 KVMem、开启 KVMem 的服务端默认 replay/128-token block。
  另保留 snapshots/32-token block 的诊断组。每组预热一次，测量两次。
- 首 token 计入预填充，生成速度用其后 255 个 token 除以首末 token 的时间差。

该测试考察共同容量范围内的基础接入成本；超预算检索和 256K 工具长任务不属于本批性能结论。

## 结果

| 配置 | 预填充 token/s | 生成 token/s | 生成相对原生 | 显存峰值 MiB |
|---|---:|---:|---:|---:|
| 纯原生 v0.7.0 | 564.10 | 37.94 | — | 14703 |
| 带补丁、关闭 KVMem | 566.14 | 37.75 | -0.51% | 14703 |
| KVMem 默认 replay | 558.30 | 36.78 | -3.05% | 14391 |
| KVMem snapshots 诊断组 | 558.88 | 35.54 | -6.32% | 14827 |

默认 replay 的预填充下降 1.03%，首 token 平均耗时从 65.35 秒到 66.03 秒。
两轮生成速度分别为 37.01 和 36.56 token/s。四组共 12 轮的 256 个输出 token 均一致，
每轮 drafted/accepted 都是 232/178，最终记录没有内部解码错误。

本次基础接入在这组配置下没有大幅性能回退；默认模式仍有约 3.1% 的生成开销，不是完全无损。
只有一个模型、一张 GPU、一个固定负载、两次正式重复，不将该结论外推到所有场景。
数据见 [完整测量摘要](benchmarks/llamacpp-v070-base-20261018.json)。原始日志保存在本机实验目录的 `performance/` 下。

上述基础接入测量之后仅修正了内存描述符中的旧版本文字，并增量构建；计算和内存管理路径未再改动。

## 状态提交与 Host 准备重叠

后续优化以 `8a5843e8` 为基线。共性规则是：状态提交可以异步进行，但依赖它的计算、
检查点和释放必须遵守完成边界。公共 KVMem 接口、传输完成和 publish 规则保持不变。
实现放在各适配器中：llama 为目标 context 的设备流加入 Fold 完成事件依赖；
NInfer 在普通 Fold 之前取回候选统计，让 Fold 与随后的 Host 统计处理重叠。
这两项都不改 Record/Fold 数学、接受前缀或 KV 格式。

llama 的顺序验证覆盖独立 FP64 递推、所有接受边界、拒绝区 NaN 和重复复用事件。
另用真实 27B 模型在零接受、部分接受、全部接受后立即保存/恢复检查点，继续验证的状态字节
和 logits 与同步对照一致。无设备事件或无对应消费者时保持同步完成；
`KVMEM_GDN_FOLD_SYNC=1` 可以在同一二进制中选择原来的同步方式。
优化后的实际服务端也通过 27B/MTP 普通聊天及流式必选工具调用，空参数 `{}` 解析正常。
公共内存契约和前缀检查点两项核心测试通过。测试进程已退出并释放 GPU。

同一 5060 Ti、相同 36K 输入和 B/R 配置，每组预热一次、正式测两次：

| llama 模式 | 生成 token/s（每轮） | 生成平均 token/s | 提交阶段 CPU 时间 ms |
|---|---|---:|---:|
| 同步 Fold | 37.429 / 37.376 | 37.403 | 84.171 |
| 事件依赖 Fold | 37.611 / 37.518 | 37.565 | 13.297 |

生成平均提升 0.43%；两轮按顺序对应的提升分别为 0.49% 和 0.38%。
预填充平均从 560.504 到 560.432 token/s，下降 0.013%。
每轮输出 token、drafted=232、accepted=178 一致。
提交阶段统计的是 CPU 提交/等待时间，不是 GPU kernel 时间；减少约 71 ms 的提交等待，
生成全程只减少约 29 ms，不能据此声称 Fold 计算消失或此前约 3% 的开销已全部消除。

同构建关闭 KVMem 的补充参照预热一次、正式测一次，生成 37.830 token/s，预填充
567.546 token/s。相对该参照，本轮同步基线慢约 1.13%，优化后慢约 0.70%；
可归因于本次前后调整的观测提升仍只有 0.43%，不能把旧测约 3% 与 0.70% 的差额都归于此优化。
同步和事件两组显存峰值均为 14391 MiB，关闭 KVMem 为 14703 MiB。

NInfer 使用同一 27B IQ3_S `.ninfer`、B=36864、R=16384、INT8 KV、MTP=4、
关闭 ngram，预填充块为 256；只在该后端内部比较前后速度。
初轮基线虽成功，但监控记录有额外约 1.8 GiB 显存占用，用户也确认其他开发正在使用该卡；
紧接的优化版本在预填充前因可用运行时显存为 0 启动失败。这两次都排除出性能结论，
原日志保留，GPU 空闲后重做同参数对照。有效运行的显存峰值均为 14169 MiB。

| NInfer 模式 | 生成 token/s（每轮） | 生成平均 token/s | 预填充平均 token/s |
|---|---|---:|---:|
| 统计在 Fold 后读取 | 79.872 / 79.939 | 79.906 | 663.355 |
| 统计在 Fold 前读取 | 80.634 / 80.547 | 80.590 | 664.362 |

生成平均提升 0.86%，按轮次对应的提升分别为 0.95% 和 0.76%；预填充提升 0.15%。
两轮记录的输出一致，MTP drafted=221、accepted=200、fallback=0。
NInfer 的 `decode_seconds` 从约 3.135 秒增加到 3.164 秒：移动读取后，候选统计读取被计入
原生 tail 的计时区间。该内部字段覆盖范围改变，因此只保留原值，不用它计算本次速度差；
上表统一使用 `256 / generation_wall_seconds`，包含完整生成等待。
真实模型的 BF16 KV、MTP=3、前缀改写、SSD 锚点字节验证及取消后恢复也通过。

逐轮数据和排除原因见 [状态提交调度测量](benchmarks/backend-commit-overlap-20261018.json)。

本次先限定 Windows/CUDA、单卡、一个模型和共同容量范围；未验证 Linux、HIP、多卡或
256K 工具负载，不将各后端绝对速度相互比较。仅两次正式重复，增益较小，不作统计显著性承诺。
NInfer 前后忙时 SM 时钟中位数分别为 1777/1781 MHz，llama 两组均为 1777 MHz。

合并前同步 master `1723b27e`，完整保留 #145 的分批 pinned KV 搬运和 #102 的 LCP 回归。
NInfer 合并后的树与 master 仅差 `prefill.cpp` 的统计读取顺序，差分与上述已测优化逐字节一致；
版本化补丁重新生成哈希并验证可从干净基线重建。上面的性能数字仍来自 `8a5843e8` 基线，
没有在同步 #145 后重新测量完整 27B 或性能。

合并验证仅使用 RTX 5050：GDN 事件消费者/FP64 参考、公共内存契约、前缀检查点和
0.8B 六轮尾部改写通过。NInfer 采用 #145 已有四层执行夹具（3 GDN + 1 Attention，保留 MTP），
重编本次读取顺序和最新 pinned 搬运两个翻译单元。BF16 KV、MTP=3、CUDA Graph 下，
前缀恢复、原生 payload/state 精确校验、取消后恢复通过。初次 64 MiB Host 配额未触发 SSD，
覆盖断言失败；将测试夹具配额降到 12 MiB 后保持原断言通过，实际冷读 33,419,264 字节、
写入 117,288,960 字节。该裁层夹具只验证执行/内存状态，不代表模型回答质量或性能。
